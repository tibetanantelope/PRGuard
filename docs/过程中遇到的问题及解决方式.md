# 过程中遇到的问题及解决方式

## GitHub Actions CI：Redis 测试环境中的客户端生命周期问题

## 1. GitHub Actions 是什么

GitHub Actions 是 GitHub 提供的自动化执行平台。代码 push、Pull Request 或手动触发后，GitHub 会在临时 Runner 中按照 Workflow 文件执行命令。

本项目的 Workflow 是 \`.github/workflows/ci.yml\`，目标是：

\`\`\`text
提交代码 → 安装依赖 → 类型检查 → Lint
        → 启动 Redis/PostgreSQL → 单元测试和集成测试
\`\`\`

这样可以在干净、可重复的环境中验证代码，而不是只依赖开发者本机环境。

## 2. 当前 CI 如何触发

\`\`\`yaml
on:
  push:
    branches: [main, master]
  pull_request:
\`\`\`

因此 push 到 \`main\`/ \`master\`，以及创建或更新 Pull Request，都会触发 CI。

查看入口：[PRGuard Actions](https://github.com/tibetanantelope/PRGuard/actions)

## 3. 当前 Workflow 每一步的作用

### Service containers

CI 启动两个临时服务：

- \`redis:7-alpine\)：测试 Redis Streams、ACK、Pending 和消息接管；
- \`pgvector/pgvector:pg16\)：测试 PostgreSQL + pgvector 长期记忆。

两个服务都配置了 health check，只有服务健康后才进入测试。

### Checkout 和 Node.js

\`\`\`yaml
actions/checkout@v4
actions/setup-node@v4
\`\`\`

前者拉取当前提交，后者安装 Node.js 22 并启用 npm 缓存。

### Install dependencies

\`\`\`bash
npm ci
\`\`\`

根据 \`package-lock.json\` 精确安装依赖，保证 CI 和本地版本一致。

### Type check

\`\`\`bash
npm run check
\`\`\`

执行 \`tsc --noEmit\`，检查 TypeScript 类型错误，但不生成文件。

### Lint

\`\`\`bash
npm run lint
\`\`\`

检查代码风格和潜在问题。warning 不会让当前 Workflow 失败，error 才会。

### Unit and integration tests

CI 设置：

\`\`\`text
PRGUARD_REDIS_INTEGRATION=1
PR_GUARD_REDIS_URL=redis://127.0.0.1:6379
PRGUARD_POSTGRES_INTEGRATION=1
PR_GUARD_POSTGRES_URL=postgresql://prguard:prguard_dev_password@127.0.0.1:5432/prguard
\`\`\`

然后执行 \`npm test\`。集成测试通过环境变量解除 skip。

PostgreSQL Memory 集成测试使用本地 Hash Embedding，不调用阿里云 API，不需要 GitHub Secret，也不会产生费用。

\`\`\`text

\`\`\`

失败测试涉及：

- shared limiter backend；
- readiness；
- Docker sandbox readiness。

调用栈指向：

\`\`\`text
RedisReviewJobQueue.connectAndPrepare
RedisReviewJobQueue.ensureReady

\`\`\`

## 5. 根因分析

本地普通执行 \`npm test\` 时没有设置 Redis URL，项目使用内存队列，所以没有触发问题。

CI 设置了全局环境变量 \`PR_GUARD_REDIS_URL\`，但是测试传入的 \`RuntimeConfig\` 没有 \`prGuardRedisUrl\`。

队列工厂会读取环境变量：

\`\`\`ts
const url = redisUrl?.trim() || process.env.PR_GUARD_REDIS_URL?.trim()
\`\`\`

而 HTTP Server 当时只根据 RuntimeConfig 判断是否启动 Worker：

\`\`\`text
Server 判断：RuntimeConfig 没有 Redis → 启动本地 Worker
队列判断：环境变量有 Redis → 创建 Redis 队列
\`\`\`

结果是 Server 关闭时，后台 Redis Worker 仍可能继续执行 \`xGroupCreate\`，但 Redis Client 已经关闭，于是产生 \`The client is closed\`。

这是一个典型的：

- 环境变量和显式配置不一致；
- 异步任务没有正确停止；
- 外部资源生命周期管理不一致；

问题。

## 6. 修复方案

修复文件：\`src/prguard/http.ts\`

修复后，HTTP Server 和队列工厂使用同一个 Redis 配置来源：

\`\`\`ts
const redisUrl = options.runtime.prGuardRedisUrl
  ?? (process.env.PR_GUARD_REDIS_URL?.trim() || undefined)
const rateLimiter = createPrGuardRateLimiter(limit, redisUrl)
\`\`\`

Worker 启动条件也改为：

\`\`\`ts
if (!redisUrl) {
  startLocalWorker()
}
\`\`\`

最终语义：

\`\`\`text
实际使用 Redis → 不启动本地 fallback Worker
不使用 Redis   → 启动本地 Worker
\`\`\`

关键工程原则：

> 谁创建资源，谁负责关闭资源；注入进来的共享资源，不应被内部组件随意关闭。

## 8. 以后排查 CI 失败的顺序

1. 先看失败的 Step；
2. 区分 warning 和 error；
3. 找最早出现的 \`not ok\`、\`Error\` 或 \`AssertionError\`；
4. 查看测试文件和行号；
5. 检查 CI 环境变量是否改变了代码路径；
6. 检查 Service container 是否 healthy；
7. 检查连接池、Worker、Timer 和异步任务是否在测试结束后仍运行；
8. 用与 CI 相同的环境变量本地复现；
9. 修复后重新运行 check、lint、test 和集成测试；
10. 推送后确认新的 Run 使用最新 commit。

## 9. 面试表达

> 我为 Agent 项目增加了 GitHub Actions CI，并在 CI 中启动 Redis 和 PostgreSQL/pgvector 服务执行集成测试。第一次运行发现，测试环境通过环境变量启用了 Redis，但 HTTP Server 的 RuntimeConfig 没有同步感知，导致测试结束时后台 Worker 继续访问已关闭的 Redis Client。最终我统一了 Redis 配置解析和 Worker 生命周期判断，解决了异步资源关闭竞态问题。
